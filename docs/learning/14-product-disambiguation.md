# 14 产品不明确时主动中断追问:依赖具体产品却不明确 → 先问不猜

> 对应决策:DECISIONS **D76**;代码:`app/businesses/insurance.py`(SYSTEM 规则 + `_append_product_list`)、`app/businesses/premium.py`(`available_product_keys` / `calculate_premium` 缺产品清单)、`tests/test_product_disambiguation.py`。

## 这一阶段解决什么问题

座席工作台的问题是**碎片化、跨客户、常省略主语**的。最常见的两种踩雷问法:

- "那这款的免赔额是多少?" —— 依赖具体产品,但没有产品名。
- "30 岁买这个一年多少钱?" —— 依赖具体产品 + 方案,但没有产品名。

改造前模型会怎么答?看 SYSTEM 里旧规则怎么写的:"用户明确点名产品(如'尊享e生2025')…" —— 这只覆盖了**有产品名**的情况。当没有产品名时,模型要么拿**某款产品的条款**硬套(张冠李戴),要么拿**"医疗险"这类通识**笼统回答(答非所问)。

这两个都不符合铁律 3(回答必须可追溯)与诚实优先:答错产品比"少答一句"更危险 —— 客服在客户面前报错了产品数字,是很难收场的。

用户要求一句话:**根据上下文不知道是哪个产品时,主动中断询问;用户给出产品后再继续回答当前问题。**

## 设计要点

### 1. 主机制是 SYSTEM 规则(产品依赖判别是语言理解问题)

三个子规则:

1. **产品不明确必须先问**:问题依赖具体产品(保费/免赔额/保额/等待期/续保条件/能否报销/责任免除/条款细则),而**问题本身+对话上下文都无法确定**是哪款 → **不要**调 `search_knowledge`/`calculate_premium`,也**不要**直接作答,应主动中断并追问一句,然后**结束本轮**。

2. **判断"是否依赖具体产品"**:问产品自身的数字/条款/责任/细则 → 依赖,不明确就先问;问类型概念(医疗险/重疾险是什么)、一般规则、产品对比、产品清单 → 不绑定单一产品,不需要追问。这条防止模型"动不动就问"——假阳性会让本来能答的提问被打断。

3. **追问后继续原问题**:用户告知是哪款后,在后续轮次把"已确认的产品+对话里的原问题"结合继续回答该原问题,不要重复追问一遍。

为什么用 SYSTEM 规则而不是关键字判定?"是否依赖产品"是语言理解问题,中文疑问题法(反义/省略/指代)会让关键词规则大量误判:把"重疾险包括哪些病种"当成"依赖产品"去追问,就把用户本可直接回答的问题打断了。所以把判断权交给 LLM,配强规则约束,同时接受"模型行为服从度"的固有不确定性(与检索收敛/诚实优先同级别,见 D28 的注)。

### 2. 确定性只做"可靠信号":在售产品目录

追问的瓶颈不在"要不要问",而在"问了之后给什么清单"。硬编码产品名会随产品增删而失真,所以加一个确定性目录:

- `premium.available_product_keys()` —— 以费率计算器注册表 `CALCULATORS` 为权威(已注册的产品即"在售"),空则回退静态 `_KNOWN_PRODUCTS`。纯读,不触库。
- 纯函数 `insurance._append_product_list(system)` —— 把"【在售产品】尊享e生2025、安盛天平卓越馨选2025"拼到 system 末尾;`bundle()` 用它构造注入后的 system。

关键取舍:**模块级 `SYSTEM` 常量本身不变**,只在 `bundle()` 时注入。为什么?既有测试断言 `insurance.SYSTEM` 的稳定内容(如"指定险种"/"category"),回放基建也依赖稳定请求;若把动态清单写进常量,会引入抖动。所以"常量稳定、注入时拼"。

### 3. 确定性兜底:calc 缺产品给出清单

`calculate_premium` 缺 `product` 时,原返回"请指定产品(product,填产品 key 或名称)"——空泛,模型还得再猜。现改为"请指定产品…当前在售:尊享e生2025、安盛天平卓越馨选2025",让模型能照着实答/转述。这是"模型没先问、直接调了工具"时的第二道兜底。

### 4. 追问即"干净的停止",不需要新事件/UI

模型输出追问 = 一条无工具调用的文本。循环照常走 `present_answer → assistant_message(无引用)→ turn_end`,前端就是一条普通助手消息。这就是"主动中断"。**追问是文本输出,不是工具调用**,所以不需要新增 `clarify` 工具、不需要改 events 注册表、不需要前端改动 —— 这符合"澄清是业务层的回答形态,不是扩展性机器"的定位。

## 测试

`tests/test_product_disambiguation.py` 7 项:

- SYSTEM 含三条关键约束(且不误删既有的"指定险种/category"规则)。
- `available_product_keys()` 列出在售两款(尊享e生2025、安盛天平卓越馨选2025)。
- `_append_product_list` 纯函数:拼入清单;`insurance.SYSTEM` 常量本身不含动态目录。
- `calculate_premium` 缺产品 → 返回含"请在售清单"的可操作文案,`reference=[]`。
- 循环层"澄清即停":模型输出追问(无工具)→ 产物为**干净一条 assistant_message**,无 `tool_call`/`tool_result`/`retrieval` 事件、无引用角标,`turn_end.reason=completed`。
- 追问后带 history 续答:原问题 + 追问 + 用户确认产品 → 该轮能产出回答块。

改 SYSTEM 属 AGENTS 回放触发项。`tests/test_replay` 用自造 SYSTEM + 空 tools,不受影响;真实 bundle 的回放录制需真机 LLM,留待评估轮。

## 边界与后续

- **服从度**:追问是否触发取决于 LLM 是否遵守规则,单测只能验证"循环行为 + 规则存在",真机行为需复测(与 D28 检索收敛同级)。
- **产品目录来源**:现从 `CALCULATORS`(费率计算器)推。将来有"只有条款、无费率"的产品时,目录会漏 —— 届时应改为从 `documents`/知识库产品列表取。
- **"在售"措辞**:目录是"有计算器/有条款的产品",并非严格"在售状态";如需区分"在售/停售",应加产品元数据字段。
