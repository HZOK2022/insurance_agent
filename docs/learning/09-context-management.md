## 这一阶段解决什么问题

长对话下,上下文窗口有限。当前项目(insurance-agent)有三个坏现象:

1. **追问接不上**:agent_loop.turn() 只构造 conversation=[user text],不读历史(单轮)。你说"那重疾呢?"它不知道你上句聊的是重疾险。
2. **大检索结果撑爆窗口**:businesses/insurance.py 的 _format_chunks 把 top_k 块整段塞给模型,没有大小上限;tool_result.result_truncated 硬编码 False。
3. **改了没底**:改 prompt/条款后没有回放可回归(AGENTS.md 硬要求),极易"我改完=修好"的假阳性。

**不含它的后果**:回答错产品、上下文爆、历史角标失效、无法回溯模型当时依据。

## 设计要点

1. **保尾压头**:最新对话逐字保留(约窗口 16%),更早的压成摘要(可能层层再浓缩)。这既防无限堆叠,又控制"中途遗忘"(近期保真、远期有概览、细节可从日志回翻)。
2. **先剪枝后摘要**(顺序固定,参照 dsh `compactIfNeeded` 核实流程):压缩(无论 pressure/overflow)触发后,**①先给"超预算的工具结果"保头尾砍中间(确定性、无模型)→ ②用 token meter 重测 → ③若已低于阈值则【跳过摘要】(剪枝自行降压)→ ④否则才选"保留尾"(不拆工具对)并对旧对话 LLM 摘要,替换头部区间**。摘要只在"剪完仍超"时发生,读的是剪枝后的表面。
   > **触发/保留口径**:pressure 在**约 80% 窗口**(thresholdTokens = 窗口×0.8)整理;context-overflow(写爆)绕过阈值;保留**约 16% 窗口**的最近对话逐字;摘要必须比被替换区间更短(否则压缩失败)。
3. **只动对话**:系统提示词 + 工具 schema 是固定头,每次重拼、不压缩;16% 保留只针对对话部分。
   > 范围澄清:RAG agent 的上下文**只有三段** = 系统提示词(insurance.py 的 SYSTEM)+ 工具 schema(search_knowledge)+ 对话。**AGENTS.md 不是它的**——AGENTS.md 是编码 agent(dsh)的工作区上下文(以 user-role <system-reminder> 消息注入),不属于本 RAG agent,故不在本方案的统计/压缩范围。
4. **边界不拆工具对**:在"保留尾"和"要压的头"之间切,但绝不把一次工具调用从中间切开(调用与返回不能拆散)。
5. **全程 append-only**:压缩/剪枝也写成事件,被替换的原文仍在日志(可回放可审计),不覆盖不删历史。
6. **"回放"是人为/审计,不是模型自决**:要原始细节 = 人在 UI 里看全量,或开发者用 `sourceEventSeqs`/请求快照回放验证;**不给模型加"读历史"工具**(那是超出 dsh 的新增,除非确有需求)。一句话:压缩替换只动"模型眼前",日志永远是真相。

## 场景澄清:座席工作台(重要)

> 这一段修正本阶段的一个**前提**,而且**只改变"压缩该保留什么",不改机械机制**。

前面几节把"用户"想成"单个终端客户的一通长对话"。真实部署**不是**这样:

- 本助手的使用者是**线上保险销售的客服(座席)**,不是投保人本人。
- 座席**一人服务几十上百位客户**,是"边回客户、边在助手上查资料、找好的回复"。
- 他**不会**每问一句就来查一句——查询**断续、按需**,很多彼此独立。
- **无法区分当前查询对应哪位客户**:可能附一句"有个怎么样的客户",也可能**直接查自己不熟悉的问题**。

所以两个前提要改:

| 原前提 | 修正后 |
|---|---|
| 单一"用户"一长对话,跨轮追问可参考上文 | "用户"= 座席,一人多客户;查询跨客户、碎片化,不能假设"上句=同一客户同一产品" |
| 压缩目标=保留"这段对话讲到哪"(客户诉求叙述) | 压缩目标=保留**工作台的"已查明知识+口径+合规红线"**,让后续查询不重查、口径一致 |

**机械机制不变**(窗口上限、工具结果剪枝、保尾压头、事件契约、append-only、请求快照)——它们只管 token 预算与记忆卫生;**变的是"摘要该蕴含什么"** = 压缩指令。

> ⚠ 跨轮上下文(阶段A)仍要做,但**别用它假设"还是同一位客户"**:座席的追问可能跳到不同客户/不同产品。用它做**产品/术语消歧 + 口径衔接**可以,承接性话术不要靠它。

### 压缩指令(座席工作台版)
作为最后一条 user 消息追加在被压缩对话之后:

    你现在是保险销售座席知识检索工作台的上下文压缩引擎。这台工作台被坐席用来边回客户
    边查资料、找好的回复;一位坐席同时服务几十上百位客户,查询彼此独立、通常跨多位
    客户,而且无法区分当前是哪位客户。请把上方这段**座席的连续查询**浓缩成结构化
    checkpoint,让工作台在后续查询中:不重复检索已查明的知识、不给与前面口径不一致的
    答案、保持合规红线一致,并能承接上次没答全的问题。
    
    严格按下面的结构输出:每个小节都保留、按顺序;用简短要点;某节没内容就写"(无)",
    不要删节。不要试图把上下文重构成"某一位客户的一次完整会话"——多数查询并不属于
    同一位客户。
    
    ## 已查明的知识与口径
    - [已查过的产品/条款/责任、年龄与保额规则及结论;每条带产品版本、条款名、引用
      编号[n]、关键数字。作用:后续同类查询直接复用,不重复检索,如要改口须显式说明]
    
    ## 已给出的回复与话术
    - [已给坐席的参考回复/话术要点,含引用与数字,保持后续口径一致]
    
    ## 未决与可追问点
    - [没答全的、坐席很可能追问的(如年龄下一档、保额往上加、病种范围)、答应要补的、
      需转人工/审批的;以及为什么没答(缺资料/超范围/需人工)]
    
    ## 客户上下文(坐席口述,尽力而为)
    - [坐席提问时附带的客户描述("有个怎么样的客户");标注为"坐席口述、可能跨多位
      客户、非唯一标识",只用于贴近当下那次提问。若坐席直接查事实未描述客户,写"(无)"]
    
    ## 风险与合规红线
    - [该拒答/转人工/需提示健康与如实告知的点;敏感项(既往症/健康状况/职业/年龄/区域/
      收入/投保人关系);可用与禁忌的话术;监管与使用限制]
    
    ## 当前查询
    - [checkpoint 时刻:坐席最近一次问查了什么,检索/生成到哪一步,命中/用了哪些条款]
    
    ## 下一步
    - [紧接坐席最近一次查询的单一下一步:补某产品细节、补年龄/保额边界、给话术、
      提示转人工,或给出建议;没有则"(无)"]
    
    ## 关键上下文
    - [取舍与理由(尤其为什么拒答/转人工/选某产品或口径);已用产品与版本;坐席的
      检索习惯与偏好;未决合规点;继续所需数据;不变式相关:SQLite 事实源、引用绑定
      版本、答复可追溯]
    
    规则:
    - 用简体中文写简洁记录,保留关键数字、产品名、条款名、引用编号[n]与客户/坐席原话
      (措辞重要时逐字)。
    - 忠实记录坐席的纠正与反馈,以及工作台之前的改口/更正。
    - 不要提及本次压缩或上下文被压缩。
    - 只输出 checkpoint 文本,不要调用工具或做其他操作。
    - 若已有 <compacted-summary> 旧块,视为上一个 checkpoint:不照抄;保留仍为真的事实、
      丢弃过期的,把新信息合并成同一结构。

**封包**:

    这是自动生成的检查点,浓缩了之前一段对话以释放上下文。把捕获的上下文当作既定背景,
    直接在其上继续,不要复述。直接从后面的消息继续任务,不要提及本检查点。
    
    <compacted-summary>
    …(上面 8 节)…
    </compacted-summary>

**保留什么(8 节)**:

| 节 | 保留什么 | 为什么 |
|---|---|---|
| 已查明的知识与口径 | 查过的产品/条款/责任、年龄与保额规则及结论;每条带版本+条款+引用[n]+数字 | 座席反复查同类问题,结论立即可复用,避免重查/答不一致 |
| 已给出的回复与话术 | 已给坐席的参考回复/话术要点 | 不重复生成、口径一致 |
| 未决与可追问点 | 没答全的、很可能追问的、答应补的、需人工/审批的、为什么没答 | 承接上次没给全的 |
| 客户上下文(坐席口述) | 问题里附带的客户描述,标注"坐席口述、可能跨多客户、非唯一标识" | 只用于贴近当下那次提问,不当身份 |
| 风险与合规红线 | 该拒答/转人工/提示健康告知的点、敏感项、禁忌话术 | 跨查询一致,保险销售重点 |
| 当前查询 | 坐席最近一次问查了什么、检索/生成到哪步、用哪些条款 | 精确接续最近一次 |
| 下一步 | 紧接最近一次查询的单一动作:补细节/补边界/给话术/提示转人工/建议 | 单一下一步 |
| 关键上下文 | 为什么选某产品/口径、产品版本、坐席检索习惯、未决合规点、缺的数据、SQLite 事实源+引用可追溯 | 决策/偏好/约束 |

**记忆**:这不是"一客户的续聊",而是"工作台的知识/口径/红线状态";客户描述只是尽力而为的辅助,不是身份。

## 关键坑(先记住)

- **旧回答的 [idx] 是当轮编号**,喂进下一轮会串(下一轮的 [1] 可能对应不同 chunk)。history 里要**剥掉旧 [n]**,或改为结构化 citations(每条 {idx, chunk_id} 与当轮检索绑定)。
- **只截断"喂模型的 content",不截断"落库的 reference"**。检索快照(含原文)要完整进 retrieval 事件,否则引用/历史角标断掉(铁律 3)。

## 阶段C 压缩的实现(已落地)

**触发**:
- **pressure**:回合开始(构造 conversation 后)与**回合中每步 LLM 请求前**,都检查 `system+tools+对话` 是否超过 窗口×0.8;跨过即压。
- **context-overflow**:回合中超过**硬窗口**时立即压(不卡 80%)。

**流程**(app/loop/agent_loop.py `_compact_conversation`,生成器):
1. `estimate(conversation) ≤ budget` → 不压。
2. 先 `prune_tool_messages` 剪工具结果(无模型)→ 重测 → 若已低于预算 → 跳过摘要(剪枝自行降压)。
3. `select_keep_tail` 从尾部往回累加到 retain=窗口×0.16,**不拆 tool_call/result 对**。
4. **先 yield `compaction_start`**(前端据此显示"压缩中"),再调 LLM 按 §8.3 指令摘要头部(阻塞)。
5. 摘要必须严格短于被替换区间;否则 yield 一个"失败"的 `compaction_end`(chars_saved=0)并回退(只丢历史正文、不拆工具对)。
6. 成功则 yield `compaction_summary`/`compaction_end`,头部替换为一条 system 帧包(`CHECKPOINT_PREAMBLE + <compacted-summary>`)。

**持久化/折叠**(app/session/context.py `build_history`):
- 遇 `compaction_summary` 事件 → 折成一条 system 帧包,跳过被 `shadowed_seqs` 命中的历史事件(append-only,原文仍在日志)。

**前端**(web/src/App.tsx):
- 收到 `compaction_start` → 顶部横幅「⏳ 上下文窗口压缩中…」;`compaction_end` → 结束;"轨迹"tab 记录 start/summary/end(带"省 N 字符")。
- 引用角标 `sources` 按**块文本 `[idx]` 位置映射检索 chunks**(不依赖服务端去重后的 citations),避免"同 chunk_id 去重"导致某些 `[idx]` 不可点。

**配置**:`compaction_threshold_ratio=0.8` / `compaction_retain_ratio=0.16` / `compaction_max_tokens=2000` / `max_tool_result_chars=8000`(阶段B-1 追加即限长)。

**与 dsh 差异**:dsh 工具结果"追加全量、只在压缩时裁";本项目"追加即限长"(B-1),且 `build_history` 丢弃历史工具结果(见 §8.5)。

## 你学到了什么

- 模型上下文是一张**有限白板**,靠"保尾压头"管理。
- **触发(80%)含 system+tools+对话;保留(16%)不含 system+tools**。
- 压缩 = **先剪工具结果(保头尾+标记),再压对话摘要**;**边界不拆工具对**;压缩后 = 摘要 + 最近保留。
- **继续压缩**会把上一段摘要也卷进新摘要("摘要的摘要"),从而防无限堆叠、控制遗忘。
- 一切写成事件(append-only),可审计可回放;引用/溯源不因压缩失效。
